sleep() vs auto-wait

A pretend checkout page (the fictional Pecan Hollow Outfitters) renders its Pay button late: it is attached, then shown, then slides into place, then enabled once prices load, and sometimes a "loading offers" overlay covers it for a while. Every delay is drawn from a seeded random generator. Three versions of the same test race over many runs: click Pay, then check that the receipt says "Paid".

The race

A slow run (think: a loaded CI machine) stretches all of that run's delays 3×. Results update as you type.

Three strategies

A · fixed sleep
await page.waitForTimeout(S);
await pay.click({ force: true }); // no checks
await page.waitForTimeout(S);
expect(await receipt.textContent()).toBe('Paid');
B · auto-wait click, one-shot check
await pay.click();   // waits until actionable
expect(await receipt.textContent()).toBe('Paid');
C · auto-wait click, web-first assertion
await pay.click();
await expect(receipt).toHaveText('Paid');   // retries

B shows the trap: auto-waiting covers the action, not the plain value you read afterwards. Only when the receipt is already there (a cached response, 30% of runs) does its one-shot check pass.

    What a Playwright click waits for

    Before locator.click(), Playwright checks that the element is visible, stable, receives events and is enabled, re-checking until all pass or the timeout runs out. Attached comes first: the locator has to resolve to an element in the DOM before anything else can be checked. fill() also needs editable; hover() skips enabled.

    Attached

    The element is connected to a Document or a ShadowRoot.

    Here: the Pay button isn't in the DOM at all until it is rendered.

    Visible

    A non-empty bounding box and no visibility:hidden. display:none or zero size fails; opacity:0 still counts as visible.

    Here: it is attached with display:none, then shown (and faded in, which does not delay visibility).

    Stable

    The same bounding box for at least two consecutive animation frames, so a click doesn't land where the element used to be.

    Here: it slides in from the right before it settles.

    Enabled

    Not disabled: no disabled on a button, input, select, textarea, option or optgroup, not inside a disabled fieldset, and not under aria-disabled="true".

    Here: disabled until the prices load.

    Receives events

    The element itself is the hit target at the click point: nothing else, like an overlay, spinner or cookie banner, is on top.

    Here: in half the runs a "loading offers" overlay covers it for a while.

    Web-first assertions such as expect(locator).toHaveText() keep re-querying until they pass or the expect timeout (5 s by default) expires. Playwright's own docs warn against page.waitForTimeout() in real tests for exactly the reason the sweep shows. Real Playwright retries on a short growing back-off; this lab polls at a fixed interval so the arithmetic stays easy to follow.
