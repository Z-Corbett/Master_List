HTTP Cache Lab

A browser's HTTP cache is a card catalogue with due dates. Set the response headers for six resources, move the clock forward, and ask for them again. Each request shows whether the cache could answer on its own, had to check with the server, or had to fetch the whole thing again, and the exact headers that went back and forth.

Freshness (RFC 9111 §4.2)

A stored response is fresh while its age is below its freshness lifetime: max-age if present, otherwise a heuristic. Here the heuristic is 10 % of the time since Last-Modified (§4.2.2 suggests that figure). With no max-age and no Last-Modified the lifetime is 0. no-cache stores the response but forces validation before every use; no-store stops it being stored at all.

Validation (§4.3)

A stale response isn't thrown away. The cache sends If-None-Match (from the ETag) and If-Modified-Since (from Last-Modified). If the server answers 304 Not Modified, the stored copy is freshened with the new headers (§4.3.4); a 200 replaces it. Vary adds request headers to the cache key (§4.1), and Vary: * never matches.

Extensions and reloads

stale-while-revalidate (RFC 5861) serves a stale copy at once and refreshes it in the background. must-revalidate forbids serving stale, so offline you get a 504 instead (§4.2.4). immutable (RFC 8246) tells the browser not to revalidate a fresh response on reload. Reload here means sending max-age=0; a hard reload sends no-cache and skips the cache.
Simplifications: one private browser cache, zero network latency (so Age is simply now minus the response time), no Expires or Age headers from the origin, heuristic freshness fixed at 10 %, and 'reload' semantics are generic, since real browsers differ. Directives not modelled here, such as s-maxage, public and proxy-revalidate, are shown as unrecognised. The resources are fictional.
