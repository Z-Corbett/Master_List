Difficulty Retarget

Bitcoin aims for one block every ten minutes, but miners come and go. Every 2016 blocks, every node recomputes the target from how long those blocks actually took. This page runs that rule on made-up hashrate scenarios so you can watch block times drift and the difficulty chase them. Hashrate and difficulty are relative (both start at 1.0), block times are drawn from an exponential distribution, and timestamp rules and real history aren't modelled.

The rule

expected = 2016 × 600 s = 1,209,600 s (14 days)
actual = time(last block) − time(first block) of the period
actual = clamp(actual, expected ÷ 4, expected × 4)
new target = old target × actual ÷ expected

Difficulty is inversely proportional to the target, so it moves by expected ÷ actual. Blocks that came too fast lower the target (harder), and slow blocks raise it. The clamp means one retarget can never change difficulty by more than a factor of 4 either way.

The off-by-one

Bitcoin Core measures from the first block of the period to the last, which spans 2015 intervals rather than 2016, yet compares it with 2016 × 600 s. At steady hashrate the difficulty therefore settles where blocks average 600 × 2016⁄2015 ≈ 600.3 s. And because consecutive windows don't overlap, the interval between one period's last block and the next period's first is never measured at all, which is the root of the known "time warp" attack. Changing it would take a consensus change, so the quirk stays. Tick "measure 2016 intervals" below to see the hypothetical fix settle at exactly 600 s.
