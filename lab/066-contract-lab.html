The Consumer. Larder, a fictional grocery app. It writes down only the fields it actually reads, as a small JSON Schema per interaction, plus the requests it sends.

The Provider. Pantry API, a fictional service. It ships four versions. Each release is checked against every consumer's contract before anyone deploys.

Article I · The consumer's expectations

What Larder relies on

Pick a consumer release and an interaction. The schema is live: edit it and the matrix below re-runs. Supported keywords: type, required, properties, items, enum, format (email, date-time).

What Pantry API ships

The provider's own view is a static diff between versions. It can tell you what changed, but only a consumer's contract can tell you who actually breaks.

      Larder and Pantry API are made up. The validator on this page is a small hand-written subset of JSON Schema: format is asserted (many real validators treat it as an annotation unless told otherwise), integer means a number with no fractional part, and unknown keywords are ignored. The breaking/safe rules follow the usual tolerant-reader reasoning: adding response fields is safe, removing, renaming or retyping them is not, and making a request field required breaks every caller that doesn't send it.
