Flaky Test Rescue Three real bugs, root-caused.

This portfolio's Lab runs hundreds of Playwright tests in CI. For five runs in a row, retries quietly turned the same failures green. When I made CI fail on any test that only passes on retry, three flaky tests surfaced. None of them was a bad test: each was a real race in the page. Below is each one as it happened in this repo, with the real diffs, a model you can slow down to watch it break, and the test that now guards it.

3real page bugs, not test bugs
400/400passes at --repeat-each=20 for the first two fixes; 180/180 at --repeat-each=10 for the third

First, stop retries from hiding it

commit 12b4f6bplaywright.config.ts

CI retried each failing test once. That's worth keeping, since the retry records a trace. But a test that failed and then passed was reported as flaky and the run stayed green. For 5 consecutive runs, the summaries read like this:

3 flaky / 521 passed
2 flaky / 4 skipped / 518 passed

One setting changes that: failOnFlakyTests. A pass on retry now fails the run.

playwright.config.ts 
  // CI retries once so the trace of a failure gets recorded, but a test that only passes on retry  // still fails the run: retries had been quietly hiding the same flaky tests for five runs.  retries: process.env.CI ? 1 : 0,  failOnFlakyTests: !!process.env.CI,

The Space bar that went to a hidden button

What CI showed

"physics is deterministic per seed" flaked in all 4 of the runs checked, on desktop and mobile, and "the plunger: a longer pull launches harder…" flaked 3 times. Each passed on retry. The ball never left the plunger lane:

Error: expect(received).toBeLessThan(expected)
Expected: < -800
Received:   0
Error: expect(received).not.toEqual(expected) // deep equality
Expected: not [[373, 680.0199652777778], [373, 681], [373, 681], ...]

Reproduce it

Code version

    This is a timing model of the race, not a recording of Chrome. "Slow the browser" delays Chrome's deferred focus fix-up past the moment the test's key press arrives, which is what a loaded CI machine does.

    The root cause

    Clicking Start focuses the Start button, and the start code hides the overlay that contains it. A hidden element can't keep focus, but Chrome doesn't move focus away at once: it fixes it up a little later. If Playwright's keyboard.down('Space') lands in that gap, the key event targets the hidden button. The game deliberately ignores Space aimed at a button (so Space can still press buttons), so the plunger never moves.

    The candle lit by a late event

    commit 12b4f6blab/061-chapel-candles.htmlflakyfixed

    What CI showed

    "extinguishing freezes the wax; relighting carries on from where it stopped" flaked in 3 to 4 of the 5 CI runs before the fix, on desktop and mobile. The test lights a candle, fast-forwards the fake clock two hours and expects 75% of the wax to remain. The candle said it had been lit just now:

    Error: expect(locator).toContainText(expected) failed
Locator: getByTestId('d-meta')
Expected substring: "75% of the wax remains"
Received string:    "Lit just now · about 8 h 00 min left · 100% of the wax remains"
    Source: the GitHub Actions logs, quoted verbatim (trimmed).

    Reproduce it

    Code version

      A timing model of the race. "Slow the browser" delays the dialog's queued close task until after the test has already fast-forwarded the clock.

      The root cause

      The candle was lit in the dialog's close event handler. Submitting a <form method="dialog"> hides the dialog straight away, but the close event is queued to fire as a later task. Playwright saw the dialog hidden, moved the fake clock forward two hours, and only then did the page run light(), stamping the candle with a time two hours late. The fix lights the candle in the form's submit handler, which runs before the dialog closes.

      Before and after

      "Saved locally" that wasn't

      commit 3ebfb98lab/032-pixel-press.htmlcaught by the gatefixed

      What CI showed

      The new failOnFlakyTests gate caught this one on its very first run, and it blocked that deploy. "exports a scaled PNG, imports it back, and autosaves across reloads" [mobile] imports an image, waits for "Saved locally", reloads, and reads a pixel back. The pixel was gone:

      Error: expect(received).toBe(expected) // Object.is equality
Expected: "#c2185b"
Received: null
      Source: the GitHub Actions logs, quoted verbatim (trimmed). Before the gate, a retry would have hidden this one too.

      Reproduce it

      Code version

        A timing model of the race. "Slow the browser" makes the 250 ms debounce timer fire late, as timers do on a busy main thread, while the test reloads on its own schedule.

        The root cause

        Autosave was debounced by 250 ms, but the status line kept showing the previous "Saved locally" while the new write was still pending. So the test's wait for "Saved locally" passed at once, on stale text, and the reload could beat the timer. A user who closed the tab quickly would have lost the edit the same way. The fix shows "Saving…" until the write lands and flushes any pending save on pagehide and visibilitychange.

        Before and after

        lab/032-pixel-press.html · the fix 
          // Debounced autosave.         This one got a new check: draw, confirm the status honestly says "Saving…", reload immediately, and expect the pixel to survive. With it, the Pixel Press spec passed 180/180 at --repeat-each=10.

        How I run a Flaky Test Rescue

        1. Make the flake visible. Turn on failOnFlakyTests in CI, keeping one retry for its trace, and list every test that has needed a retry.
        2. Reproduce it on demand. Run the suspects with --repeat-each and retries off, under load if need be, until the failure rate is a number rather than a feeling.
        3. Ask what the test assumes has already happened. Read the trace and the event order: focus moves, queued events, debounced timers, repaints. Each case above was an assumption that held on a fast machine.
        4. Fix the cause, wherever it lives. All three here were page bugs, and real users could hit them too. When the test is at fault, fix the test: in the same commit, a spec that slept 200 ms waiting for a repaint now polls with expect.poll.
        5. Prove it and guard it. Hundreds of repeats with zero failures, a regression check that acts as fast as a user can, and a short written report of every cause.
